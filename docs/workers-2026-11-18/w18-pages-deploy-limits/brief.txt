배경
- 핵심 서비스는 두 가지다: 지역(인구) 분석, 상권 분석.
- 앞으로 수직 확장(기간·분석 깊이)과 수평 확장(지하철역, 버스 정류장·노선, 부동산)이 예정돼 있다.
- 현재 배포 방식
  - scripts/publish-pages.py가 dist(= 빌드 + public/data 전체)를 gh-pages 브랜치로 푸시한다.
  - 공개 주소: https://ilovejsbach.github.io/seoul-audience-brief/
  - 서버와 인증키는 없다.
- 다른 작업자 w17(창3)이 프로그램 구조 전반(데이터·백엔드·프론트)을 점검 중이다. 이 작업은 "배포·호스팅 방식"에 집중한다. 결과는 감독자가 합친다.

할 일
1. 현재 실측
   - public/data 자료별 파일 수, 총 용량, gz 여부, 가장 큰 파일
   - dist 총 용량
   - 첫 화면 진입 시 내려받는 바이트와 요청 수. 로컬 vite preview에서 Playwright로 측정하고 PC 1365로 한다.
   - 공개 사이트도 같은 방법으로 읽기 전용 측정한다. GET만 사용한다.
   - gh-pages 브랜치 이력의 크기를 잰다. 예: git count-objects -vH, git rev-list --objects gh-pages | 크기 상위.
     - 배포 때마다 데이터가 다시 커밋되며 저장소가 커지는 문제가 있는지 확인한다.
     - git 명령은 읽기 전용만 쓴다.
   - 공개 사이트의 응답 헤더(Cache-Control, ETag, Content-Encoding)를 확인한다. gz 파일이 이중 압축되는지, 캐시가 몇 분인지 본다.
2. GitHub Pages 공식 제한 확인
   - 외부 요청은 GitHub 공식 문서(docs.github.com)만 허용한다.
   - 확인할 항목
     - 사이트 크기 한도
     - 파일 크기 한도
     - 월 대역폭
     - 빌드·배포 횟수
     - 저장소 권장 크기
     - 비공개 저장소 Pages 조건
     - 상업적 사용 제한(이용약관상 Pages의 용도 제한)
   - 각 수치에 문서 URL과 확인 날짜를 붙인다. 문서에서 찾지 못한 것은 "미확인"으로 표시한다.
3. 성장 시나리오 추정
   - 현재 증가 속도를 계산한다(생활인구 하루치 gz 크기 × 날짜 수 등).
   - 다음 시점에 사이트 크기, 저장소 크기, 첫 로딩이 어떻게 되는지 추정한다.
     - 1년 뒤
     - 지하철·버스 추가 시
     - 부동산 추가 시
   - 어느 시점에 어떤 한도에 먼저 닿는지 표로 정리한다.
4. 데이터 보호와 공개 범위 확인
   - 정적 공개 방식에서는 모든 데이터가 누구에게나 내려받아진다. 이것이 공공데이터 이용 조건이나 광고주 대상 서비스 성격과 충돌하는지 점검한다.
   - 접근 제어가 필요해질 경우 정적 방식으로 가능한지도 점검한다.
5. 대안 비교
   - 아래 선택지를 비교한다. 수치가 확인되지 않은 것은 "미확인"으로 둔다.
     ① 현행 유지 + 개선: 데이터 분할·지연 로딩, gh-pages 이력 정리(orphan, 단일 커밋 강제 푸시), Actions 배포 전환
     ② 데이터만 분리 호스팅: 객체 저장소(S3·R2·GCS)나 GitHub Releases. 화면은 Pages에 그대로 둔다.
     ③ 정적 호스팅 교체: Cloudflare Pages, Netlify, Vercel
     ④ 서버·API 도입
   - 비교 기준: 비용, 운영 부담, 용량·대역폭 한도, 접근 제어, 캐시 제어, 현재 구조와의 전환 난이도
   - 언제 어느 단계로 넘어갈지 전환 기준을 정한다(용량, 주제 수, 접근 제어 필요 여부).
6. 지금 바로 할 수 있는 저위험 개선을 제안한다.
   - 예: gh-pages 이력 비대화 방지, 캐시 무효화 방식, 첫 로딩 줄이기
   - 각 제안에 바뀌는 파일과 검증 방법을 적는다.
