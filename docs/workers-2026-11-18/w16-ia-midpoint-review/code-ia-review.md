# w16 코드·문서 IA 독립 검토

2026-11-18 · 기준 HEAD `e7422c1`. 코드/현재 로컬 정적 자료/지정 문서를 읽은 검토다. 실제 화면·실측·스크린샷·조건 왕복은 부모 검수와 합쳐 판단한다. 소스·public·기존 문서 변경과 외부 요청은 하지 않았다.

## 핵심 판단

1. 사용자가 확정한 서비스 경계는 **지역 분석 → 분석/시연**, **상권 분석 → 모드 없음**이다. 현재 UI도 상권 안에는 모드 선택기가 없지만, 시작에서는 모드가 먼저 보이고 상권은 별도 버튼으로 진입해 두 서비스가 같은 위계로 드러나지 않는다.
2. 수직 심화는 이미 꽤 있다. 지역 자료별 상세 5–8개와 상권 상세 3개가 존재한다. 기능을 추가하기 전에 이름·지원 범위·현재 서비스·복귀의 발견성을 다듬는 편이 우선이다.
3. 수평 확장은 탭 4개를 7개로 늘리는 것으로 해결되지 않는다. 슬롯·상세 프레임은 재사용할 수 있지만 구/동·상권·역·노선·필지의 관계와 집계는 별도 계약이 필요하다.

## 현재 코드 IA와 상태 경계

```text
시작(view=overview)
 ├ 브랜드: 상권·인구 분석 / 광고 입지 전략 → 시작
 ├ 헤더: 상권 지도 → 별도 상권 서비스
 ├ 헤더: 분석용 / 시연용 → 지역 분석을 표현하는 mode 상태
 └ Hero
    ├ 분석용: 생활인구 / 생활이동 / 거주지 전입·전출 / 행정동 추정매출 카드
    ├ 시연용: 브리핑 자료 선택 → 위 4자료
    └ 이전 분석/시연 이어보기(방문 후)
지역 분석(view=analysis)
 ├ 자료 탭: 생활인구 / 생활이동 / 거주지 이동 / 추정매출
 ├ 보기: 지도 / 상세 분석(자료별 항목)
 ├ 서비스 이동: 상권 지도
 ├ 배치 설정
 ├ 지역 모드: 분석용 / 시연용
 ├ 더보기: [시연만 근거 정보 보기·접기] / 시작 화면 / 브리핑 인쇄
 ├ 조회: 자료에 맞는 실제 입력 한 벌
 ├ 지도 도구: 구/동, 확대/이동, 색상·표시, 범례

상권 분석(view=map, UI상 별도 모드 없음)
 ├ 상단: 상권 지도 · 유동인구와 매출
 ├ 작업: 지역 정보 열기/닫기 / 상권 창 배치 / 지역 분석 지도
 ├ 조회: 자료(추정매출/유동인구), 분기, 구/동, 이름검색, 상권유형
 ├ 추가 조회 옵션: [매출만 업종] / 비교 항목 하나 / 세부 항목
 ├ 공간 경로: 서울 전체 → 구 → 선택 상권
 ├ 상세 분석: 선택 상권 추이 / 두 분기 비교 / 후보 상권 비교
 ├ 결과 도구: 지도 표시 / 출처·경계·해석 기준 / 표 내려받기
 └ 지도 도구: 축소/배율/확대/원래 범위/범위 맞춤, 조건부 필터 해제, 범례
```

## 두 매출은 어디가 다른가

| 항목 | 행정동 매출 | 상권 매출 |
|---|---|---|
| 서비스·진입 | 지역 분석의 ‘추정매출’ 탭 | 상권 지도 서비스의 자료 ‘추정매출’ |
| 원본 | OA-22175 | OA-15572 |
| 준비 단위 | 분기×행정동, 제공63업종 합계 | 분기×상권×제공62업종 |
| 공간 | 구/동 코드 | 상권 도형·코드, 보유 경계 대표 구/동 |
| 지원 조건 | 제공6시간대, 개별 업종/성/연령/요일 선택 없음 | 업종과 시간/성/연령/요일 중 한 가지 |
| 후보 | 구/동 후보 | 상권 후보 |
| 기간 | 현재 둘 다 2025Q1–2026Q2 | 기간이 같아도 공간·업종 범위는 별개 |

구/동 매출과 상권 매출을 같은 테이블로 합치거나 경계를 행정동처럼 더해 총계를 맞추는 제안은 부적절하다. 원·분기가 같아도 원본 공간·포함 업종·중첩 가능성이 다르다. 같은 단위라는 이유로 상호 대체하거나 인구당 매출/구매전환율을 만들지 않는다(R18).

## 목표안 검토에 적용할 반박 기준

- 상권을 지역 시연 모드 아래로 편입하거나 모든 서비스에 분석/시연 버튼을 복제하면 최신 확정과 충돌한다.
- ‘매출 하나로 통합’이 이름 찾기를 줄여도 공간·업종·모집단을 섞으면 데이터 계약을 위반한다. 명칭/서비스 경로를 통일하되 원본과 값은 합치지 않는다.
- 자료7개를 대비한다며 새 전역 메뉴·라우터·백엔드·저장을 한 번에 도입하면 현재 공간·가독성·동작 우선 요구를 어긴다.
- 상세8개가 많다고 모두 한 화면에 펼치면 원래의 스크롤·주정보 축소 문제를 재발시킨다. 질문별 콤보와 가까운 후속행동의 발견성을 먼저 다룬다.
- 모드/서비스 전환의 ‘보존’은 원래 문맥을 잃지 않는다는 뜻이다. 지원하지 않는 조건을 다른 자료로 몰래 복사하거나 복귀 때 사용자 명시변경을 취소하면 안 된다.
- 4열을7열로 줄이기만 해서는 동일 크기·가독성·지도공간을 증명할 수 없다. 두 PC 폭에서 실제7자료·긴 한글명을 넣은 시안과 도달 과업을 검사해야 한다.
- 점·선·면 프레임 공유는 집계·공간관계 공유를 뜻하지 않는다. 교통/부동산 데이터 확보 전 활성메뉴·샘플통계를 현재 서비스 지원으로 표시하지 않는다.

요구서가 상권 기간/검수를 일반적으로 ‘두 모드’라고 적은 조항은 최신 사용자 전제에 맞게 범위를 해석해야 한다. 현장 협의를 상권 작업공간에서 수행할 수 있다는 것과 별도 상권 시연 모드를 제품에 만든다는 것은 다르다.

## 부모 목표안에 대한 자기 반박

### 최소안: 두 서비스 진입/명칭 명확화 + 지역만 모드

방향은 현재 과제와 맞지만 다음 반례를 통과해야 한다.

1. **서비스 둘을 보이게 하려다 시작 화면을 크게 갈아엎는가?** 이미 상권 진입 버튼이 있고 지역 자료는 바로 열린다. 발견성 개선이 목적이면 먼저 서비스 이름과 적용범위·두 매출 이름을 정리하는 안을 현재 PC 화면에서 비교한다. ‘서비스 선택’ 단계를 강제해 숙련 사용자의 바로가기에 클릭만 추가하면 개선이라고 말할 수 없다. 두 거대 카드·별도 허브/새 전역 메뉴는 이번 최소안의 필수 조건이 아니다.
2. **모드 범위 제한을 단순히 `setMode('analysis')`로 처리하면?** 상권으로 갈 때 지역 시연 설정을 잃고 복귀에서 달라질 수 있다. 지역 모드 상태는 보존하되 상권 DOM/CSS에는 영향을 주지 않는 경계를 검토해야 한다. 지역 분석/시연 각각→상권→지역 복귀에서 지역 모드·기간·지역·후보와 상권 독립 조건이 유지되는지 확인해야 한다.
3. **‘행정동 추정매출’로 이름을 늘리면 헤더가 다시 두꺼워지는가?** 현재 고정4열/nowrap이다. 작은 글자로 해결하지 말고 두 PC 폭의 탭 균등·모드/상세/상권 버튼·긴 이름을 실측한다. 자료 탭·제목·원본 안내에서 공간 단위를 함께 일치시키는 것이 목적이며 모든 숫자마다 긴 접미사를 반복할 이유는 없다.
4. **다른 서비스의 조건을 자동 전달해야 한다고 오해하는가?** 현재 보존은 독립 문맥 보존이다. 생활인구의 특정 날짜/성·연령이 상권 분기/주변분포와 같다는 가정은 금지한다. 이름을 명확히 해도 지원 조건의 의미를 새로 통합하지 않는다.
5. **상권에서도 협의하려면 시연 모드가 꼭 필요한가?** 아니다. 동일 상권 작업공간에서 후보/분기/항목을 바꾸며 대화할 수 있다. ‘상권은 모드 없음’을 이유로 상세·출처·정확값을 줄이거나 현장 비교 기능을 없애서도 안 된다.

최소안 검수 질문: 처음 온 사람이 지역과 상권 중 목적에 맞는 서비스를 고를 수 있는가, 두 매출의 공간 단위 차이를 설명할 수 있는가, 어느 모드가 어느 서비스에만 적용되는지 알 수 있는가, 되돌아와 다시 입력할 필요가 없는가. 현재 사용자의 오선택률·완료시간은 측정하지 않았으므로 개선 수치를 주장하지 않는다.

### 수평 확장 직전안: 주제 설명서/레지스트리 + 공간·기간 어댑터

1. **7개 자료 때문에 지나치게 큰 범용 프레임을 만드는가?** 현재4자료를 즉시 갈아타게 하는 전면 이관은 비용/회귀 범위가 크다. 첫 새 주제를 실제로 확보한 뒤 필요한 메타와 한 어댑터만 먼저 만들고 기존 셸·상세·표시/출처 부품을 점진적으로 연결한다. 현재4자료는 비교 기준으로 보존한다. 레지스트리라는 이름의 거대한 메뉴/필터 자동생성기를 먼저 만드는 것은 이 안의 필수조건이 아니다.
2. **주제·자료·공간 객체를 다시 한 목록에 섞는가?** 지역/상권은 현재 서비스 경계, 이동/매출은 자료, 역/정류장/필지는 공간 객체다. 설명서는 이 세 축을 각각 기술해야 하며 자료7개를 무조건 같은 탭행에 놓는 구조를 정당화하면 안 된다. 필요할 때 서비스/주제별로 지원 자료를 고르는 구조는 후보안이지 새 서비스 이름의 사용자 확정이 아니다.
3. **점·선·면을 그린 사실로 관계와 집계가 해결됐다고 여기는가?** 역의 여러 노선/출입구, 버스의 방향·정류장 순서, 부동산의 단지/필지/거래 표본은 다른 연결이다. ID, 표시 geometry, 부모/관련관계, 집계/단위, 지원 시간해상도, 결측을 따로 다룬다. 지도 셸의 `children`은 재사용하되 상권의 gu/dong 코드를 공통부모로 강제하지 않는다.
4. **기간 어댑터가 일·분기·연을 자동으로 환산하는가?** 선택 UI/정렬·범위 표시만 공통화하고 원본 주기는 그대로 둔다. 생활인구 한 날짜24시간, 생활이동 원본일자/출발·도착, 연간 전출입, 분기매출을 같은 point 배열에 넣는 것만으로 서로 비교 가능해지지 않는다. 지원되지 않는 전년동기는 비활성/이유를 제공한다.
5. **후보·비교를 공유한다며 서로 다른 단위를 한 순위로 만드는가?** 같은 조건 비교 계약은 재사용할 수 있으나 구/동 후보와 상권/역/필지 후보를 같은 숫자 비교에 자동 포함시키지 않는다. 교차주제 분석을 별도로 허가받지 않은 상태에서 공간연결·면적배분·구매전환율을 추가하지 않는다.
6. **무엇을 지금 안 해도 되는가?** 새 서버·새 인증·저장/공유·대규모 라우팅·가짜 신규 메뉴는 이 확장안의 선행조건이 아니다. 실제7자료 시안/첫 새 주제의 점·선·면 조작·독립 기대값·복귀·조건 보존 관문을 먼저 정의한다.

두 안 모두 ‘현재 화면의 작은 수정으로 목표를 풀 수 있는가’를 먼저 묻는다. 새 상권 시연 모드, 두 매출 원값 합치기, 당장 큰 개편은 제안하지 않는다는 부모의 범위가 적절하다. 다만 실제 최소안의 도달 과업과 영향 범위가 검수되기 전에는 설계안 채택 자체를 UX 통과로 보고할 수 없다.


## 실제 순회 후 보충: 표시 설정의 2px 축소 — 확인된 P1

이 절은 앞의 코드만 읽은 잠재 위험과 다르게 **부모가 실제 Orca 키보드 조작으로 재현한 현 사용 기능 결함**이다. 이번 IA 점검에서는 수정하지 않는다.

증거:

- [1365 분석 표시 설정](./screenshots/1365-analysis-population-menu4.png), [1365 시연 표시 설정](./screenshots/1365-presentation-population-menu3.png): 아이콘/내용이 지도 오른쪽 경계로 밀리고 읽을 수 있는 설정창이 보이지 않는다.
- 1920×1080에서 visible summary 초점→Orca keypress Enter로 다시 열어 재현했다. [실제 화면](./screenshots/1920-display-native-enter.png), [상태 JSON](./1920-display-native-enter.json), [기하·스타일 JSON](./display-native-enter-geometry.json).
- mapWrap: 폭1304.5px, 열너비 `1100.84px 187.656px 0px`. open mapDisplaySettings: `position:absolute`, `grid-column:3`, `grid-row:3`, width2px, offsetParent mapWrap.

원인 코드 연결:

1. `src/viewport-workspace.css:40`은 mapWrap을 `minmax(0,1fr) auto auto` 3열 grid로 만들고 `overflow:hidden`을 둔다.
2. 같은 파일 `:46`은 표시설정을 `grid-column:3;grid-row:3`의 세 번째 auto 열에 놓는다.
3. `:54`는 open 표시설정을 `position:absolute;right:8px;top:4px;width:min(340px,calc(100% - 16px))`로 바꾸지만 grid placement를 해제하지 않는다. 레이아웃에서 빠진 설정이 차지하던 세 번째 열은 실제0px이 됐고, 그 grid 영역에 남은 퍼센트 폭 계산 결과가 내용0+테두리2px로 수축했다는 설명이 실측과 일치한다.
4. `src/tableau-query-integration.css:31–36`도 `max-width:100%`, open절대배치/퍼센트폭을 가진다. 다만 최종 스타일은 더 강한 `#root` selector인 viewport 규칙이 우선하는 구조다. 단순히 하위 팔레트의 width만 늘리면 근본 containing-block/clip 문제가 남는다.

영향과 판정:

- 메뉴 DOM/하위 select가 JSON에 존재해도 사용자가 내용을 읽고 선택할 수 없다. 배경 inert 문제도 아니며 부모의 실제 키보드 조작에서도 재현됐다.
- 이는 **지도 색상·표시 설정에 도달하지 못하는 P1**이다. 서비스 전체 불능은 아니지만 부가형식의 낮은 우선순위라는 이유로 현 사용 결함을 뒤로 미루면 안 된다. 관련 R05/R06/R11/R14/R17/R20.
- 일반 MapCanvas를 사용하는 생활인구/생활이동/거주지 이동/행정동 매출이 같은 CSS 소비자다. 수집된 양모드 snapshot은 넓은 영향 가능성을 보이지만 각 자료의 모든 설정값/전체화면까지 검사한 것은 아니다. 상권은 별도 표시 팝오버이므로 이 CSS 결함의 실제 소비자라고 자동 포함하지 않는다.
- 후속 수정은 열려 있는 설정의 좌표 기준·폭·클립 경계를 바로잡는 국소 작업으로 범위를 정하고, 두 PC 폭·지역 양모드·모든 일반4자료·전체화면·지도 복귀·원값/색상범위 불변을 회귀한다. 이번 보고서는 해결 코드를 적용하지 않는다.
