# 메인 메뉴·정보 구조 중간 점검

## 1. 핵심 결론 3줄

지역 분석은 분석용·시연용을 함께 쓰고, 상권 분석은 모드 없는 별도 서비스로 명확히 보여주는 것이 맞습니다.
지금은 큰 메뉴 개편보다 잘리는 지도 표시설정, 두 매출의 이름, 서비스·모드 범위 안내를 먼저 다듬어야 합니다.
역·버스·부동산을 추가하기 전에는 탭을 늘리기보다 공간 단위·기간·지원 분석의 연결 규칙부터 준비해야 합니다.

## 2. 현재 IA 요약

2026-11-18, 소스 `e7422c1`, 로컬 Vite `http://127.0.0.1:5173/`를 점검했습니다. 4187에는 실행 중인 서버가 없어 같은 저장소의 기존 Vite를 사용했습니다. 실제 CSS 화면 크기는 1365×768, 1920×1080이며 모바일은 제외했습니다. 브리프와 지정 문서를 읽고, 별도 Codex 검토자의 [코드·문서 검토](code-ia-review.md)를 실제 화면과 대조했습니다. 공개 화면·과거 검사 결과는 이번 로컬 판정의 근거로 대신 쓰지 않았습니다.

현재 나무 구조와 노드별 위치·위계·실측·조건 보존·복귀는 [ia-current.md](ia-current.md)에 있습니다. 지역 자료별 상세 8+6+6+5개를 두 PC 크기와 두 모드에서 각각 선택하고 닫아 지도로 돌아왔습니다. 각 자료의 첫 상세는 팝업→본문→팝업도 왕복했습니다. 이는 메뉴 도달 검사이며 모든 계산·데이터 조합의 품질 통과를 뜻하지 않습니다.

상권 상세3개도 두 PC와 두 진입 경로에서 팝업·본문을 왕복했습니다(12회). 기준일11/1·12시·송파구·20–39세·남성으로 바꾼 대표 조건은 상세·전체화면·탭·모드·상권·시작/이어보기 왕복 뒤 두 PC 모두 유지됐습니다. [조건 대조](roundtrip-results.json)에 기본값 검사와 나눠 기록했습니다.

핵심 장점은 유지할 가치가 있습니다. 조회와 표시설정이 분리돼 있고, 상세에는 공통 선택기와 팝업·본문 전환이 있습니다. 네 자료 탭은 현재 두 PC 화면에서 같은 크기를 유지합니다. 상권은 별도의 공간 탐색·후보·조건을 갖고 있으며 지역 분석으로 돌아가는 목적지도 명시합니다.

반면 시작 화면에는 두 서비스가 같은 위계로 나란히 설명되지 않습니다. 지역 자료 카드와 모드가 중심이고 상권은 헤더 버튼입니다. 이것은 **발견성 위험**이지 실제 사용자가 길을 잃었다는 실험 결과는 아닙니다. [시작 화면](screenshots/01-start-1365.png), [지역 분석](screenshots/1365-analysis-population-map.png)을 근거로 판단했습니다.

기존 문서의 왼쪽 조회창·조건 칩·세로 심화문서·고정 브리핑 장면은 현재 화면과 다르거나 미래 제안입니다. 현재는 상단 실제 입력, 상세 콤보, 중앙 본문 교체가 우선입니다. 문서별 대조와 줄 번호는 [독립 검토의 문서 대조표](code-ia-review.md#문서와-코드의-차이)에 적었습니다.

## 4. 수평 축 판단

### 자료 탭이 7개 이상일 때

현재 지역 탭·시작 카드·자료 본문 분기는 4개를 전제로 합니다. `src/integrated-analysis-header.css:9`는 `repeat(4,minmax(0,1fr)) !important`, `main.tsx:163`은 4개 목록, `:182`는 나머지 3자료의 고정 렌더입니다. 1365에서는 헤더에 모드·상세·서비스 이동·배치까지 함께 있습니다.

따라서 ‘3개 버튼을 추가하면 수평 확장 완료’라고 볼 수 없습니다. 그렇다고 이번에 소스를 바꾸거나 가상 7탭을 삽입하지 않았으므로 **7개면 반드시 깨진다고 단정하지도 않습니다**. 새 주제 직전에 실제 긴 한글 이름 7개 이상을 넣은 시안으로 동위 크기, 줄바꿈, 탐색·지도 높이, 복귀를 두 PC에서 검수해야 합니다.

### 점·선·면을 넣을 위치와 공통 틀

| 새 주제 | 제안 위치·공간 표현 | 다시 쓸 수 있는 틀 | 주제별로 새로 정할 계약 |
|---|---|---|---|
| 지하철역별 이동 | 새 주제 선택 아래 역·노선 탐색. 구→동의 하위로 강제하지 않음 | 단일 조회, 지도 영역, 선택 정보, 상세/비교, 출처 | 역·노선·환승·출입구 ID와 관계, 승하차 정의, 점 중첩·선택 |
| 버스 정류장·노선 | 교통 주제 후보 안의 정류장 점·방향별 노선 선 | 지도 이동/확대·범례·선택·기간·상세 프레임 | 방향·정류장 순서·노선 관계, 시간/운행 단위, 승하차 집계 |
| 부동산 | 별도 주제 후보 아래 단지·필지·거래 | 조회/결과/상세/후보/출처의 역할 | 단지·필지·거래 ID, 가격·면적·표본수, 계약일/거래월, 표본 차이 |

이 위치는 확정 새 서비스명이 아니라 **자료 확보 후 검토할 설계안**입니다. 서비스/주제/자료/공간 객체는 서로 다른 축입니다. ‘지하철’이 추가된다고 지금 지역 자료 목록에 무조건 한 탭으로 붙이는 것은 피해야 합니다.

`MapWorkspace.tsx:11–13`의 `topQuery/details/children`과 공통 상세 프레임은 바깥 틀로 재사용할 수 있습니다. 반면 `MapCanvas.tsx:45,62–79`는 구·동과 코드 길이를, `MarketExplorer.tsx:44,53–64`는 상권·분기·업종을 전제합니다. GeoJSON이라는 형식이 같아도 선택·부모·후보·집계 의미까지 같아지지는 않습니다.

기간 UI는 제공 단위·범위·기준/선택 표시를 공통화할 수 있습니다. 일·분기·연을 자동 환산하거나 서로 다른 모집단을 같은 순위·전환율로 합치는 기능은 공통화 대상이 아닙니다. 지역의 분석·시연 표현 규칙은 재사용할 수 있으나 상권에 새 모드를 만들 이유가 되지 않습니다.

## 6. 목표 IA 제안과 단계별 계획

### 안 1 — 현재 화면을 유지하면서 경계를 명확히 하기: 우선 권고

```text
시작/공통 진입: 서비스 목적과 현재 서비스 표시
├ 서울 구·동 지역 분석             [자료 바로가기·이어보기 유지]
│  ├ 지역 모드: 분석용 / 시연용
│  ├ 자료: 생활인구 / 생활이동 / 거주지 이동 / 행정동 매출
│  ├ 조회: 자료에 맞는 단일 입력
│  └ 지도 / 상세(질문·기간 단위가 드러나는 항목) / 후보·조건 비교
└ 상권 분석                        [단일 지도 작업공간, 모드 없음]
   ├ 자료: 상권 추정매출 / 상권 유동인구
   ├ 조회: 분기·상권·업종·한 가지 주변분포
   └ 지도 / 선택 상권 추이 / 두 분기 비교 / 후보 상권 비교
공통 역할: 배치·표시 설정 / 의미·출처 / 명시적인 서비스 복귀
```

서비스 선택 화면을 한 단계 강제로 추가하자는 뜻은 아닙니다. 기존 바로가기·이어보기를 유지하면서 서비스 이름과 범위를 읽을 수 있게 하는 최소안입니다. ‘행정동 매출’ 등의 최종 짧은 이름은 실제 헤더 공간과 이해도를 확인한 뒤 정합니다. 긴 이름을 넣고 글자를 줄이는 방식은 피합니다.

장점은 현재 조회·상세·지도 틀을 보존하고 비용과 회귀 범위가 작다는 점입니다. 한계는 새 주제가 많이 늘 때의 탐색·공간 모델까지 해결하지는 못한다는 점입니다.

**지금 할 단계(후속 구현 작업):**

1. I01 표시설정 폭·위치를 먼저 고치고 4자료×2모드×2PC에서 열기·입력·닫기·원값 보존을 검사합니다. IA를 바꾸기 전에 현 조작을 정상화합니다.
2. I08/I09의 오래된 안내와 실제 메뉴 설명을 맞추고, 두 매출의 공간 단위와 서비스 목적을 명확히 합니다. 동위 크기·긴 이름·지도 가용 높이를 검사합니다.
3. 상권의 표현을 지역 모드로부터 분리하되 지역 모드 상태는 보존합니다. 단순히 상권 진입 때 `setMode('analysis')`로 덮으면 지역 시연 복귀가 바뀔 수 있습니다. 양쪽 문맥을 따로 보존하며 양방향 왕복을 검수합니다.
4. ‘두 시점’의 시간 단위와 상권 추가조건의 역할을 가까운 설명·항목명으로 드러냅니다. 실제 과업으로 서비스 선택·매출 구분·비교 찾기·복귀를 확인합니다. 사용성 개선 수치는 사용자 검사를 하기 전에는 주장하지 않습니다.

### 안 2 — 새 주제 직전에 선택 구조와 연결 규칙을 늘리기

```text
서비스/주제 선택                    [새 이름·배치는 과업/자료 확보 후 결정]
├ 기존 지역 분석 → 기존 자료 + 지역 분석/시연
├ 기존 상권 분석 → 기존 두 자료 + 단일 지도 작업공간
└ 새 주제 후보: 교통 / 부동산 …
   ├ 지원 자료 선택                 [긴 전체 7탭 상시 나열을 피하는 시안 비교]
   ├ 공간 객체·관계: 역·노선·정류장 / 단지·필지·거래
   ├ 자료가 지원하는 기간·조건
   └ 지도 / 상세 / 허용되는 비교 / 출처
공통 틀 + 주제별 공간·기간·계산 연결부
```

자료 설명서에는 서비스·주제·자료 ID, 공간 객체 ID/관계, 원본 기간 단위, 모집단·단위·집계, 지원 조건/보기, 결측·출처/버전을 적습니다. 공통 부품은 이 설명을 읽어 필요한 선택·복귀·지원 안내를 제공하고, 주제별 연결부가 점·선·면 및 계산을 맡게 합니다.

장점은 새 주제를 기존 구/동·상권의 하위로 억지 편입하지 않고 기존 상세·출처 프레임을 다시 쓸 수 있다는 점입니다. 비용은 기존 상태·조회·선택·후보의 연결부를 점진적으로 나눠야 한다는 점입니다. 메뉴·라우팅·상태를 한 번에 교체하면 지역/상권 왕복과 포털·본문·전체화면 회귀 범위가 커집니다.

**수평 확장 직전 단계:**

1. 첫 새 주제의 원자료·정의·과업을 확보하고 지원표부터 작성합니다. 미확보 메뉴와 예시 수치를 현재 기능처럼 열지 않습니다.
2. 기존 4자료는 유지하고 새 주제 하나에만 공간·기간 연결부를 적용합니다. 단순 선택형과 주제별 목록형 등 실제 7개 이상·긴 이름 시안으로 탐색을 비교합니다.
3. 점/선/면 선택·관계·후보·비교·무결과·출처·서비스 복귀를 두 PC에서 검사하고 독립 원자료 의미 대조를 추가합니다. 이 관문을 통과한 부분부터 기존 공통부품을 연결합니다.
4. 저장·주소 공유·백엔드는 실제 장기 운영 요구가 생겼을 때 따로 설계합니다. 이번 IA 점검만으로 전면 도입을 결정하지 않습니다.

### 자기 반박 결과

- 지금도 상권 버튼과 지역 바로가기가 있으므로 새 허브를 강제하면 클릭만 늘 수 있습니다. 최소한의 라벨·범위 안내부터 검수해야 합니다.
- 상세 8개가 있다는 이유로 모두 한 화면에 펼치거나 순서형 발표를 강제하면 현장 협의 목적과 충돌합니다. 질문에 따라 자유롭게 지도·조건·상세·후보를 왕복하게 유지합니다.
- 상권의 모드가 없다는 전제는 협의 기능을 줄이라는 뜻이 아닙니다. 같은 작업공간에서 조건·분기·후보를 바꾸며 대화할 수 있어야 합니다.
- 공통 틀을 쓰더라도 두 매출을 합산하거나 날짜·분기·연을 자동 환산하지 않습니다. 지원하지 않는 성별×연령 등 결합표, 광고 효과·구매전환율을 만들지 않습니다.
- 현재 4탭이 균등하다는 사실과 7개 이상 확장이 준비됐다는 판단은 별개입니다. 반대로 7개 목업을 실행하지 않았으므로 반드시 깨진다는 주장도 제외했습니다.

## 7. 미검사 범위와 한계

이번은 **로컬 PC IA 검토**입니다. 모바일·태블릿·공개 배포, 실제 사용자 이해도/오선택률, 모든 지역·기간·차원 조합, 독립 원문 수치 전수대조, 색 대비 전수·스크린리더 전수, 인쇄 결과·CSV 다운로드 내용은 검사하지 않았습니다. 외부 링크·인쇄·내려받기는 외부 요청/폴더 밖 생성 금지에 맞춰 실행하지 않았으며 메뉴 존재와 위치만 확인했습니다.

7개 이상 자료의 실제 목업과 역·버스·부동산 데이터 구현은 만들지 않았습니다. 관련 판단은 현재 코드의 제약과 새 자료의 요구를 바탕으로 한 설계 검토입니다. 모든 하위 옵션의 모든 값·드래그·재생을 전수 실행한 기능 회귀 보고도 아닙니다. 표시설정은 존재/열기와 실제 읽기 가능성을 나눠 실패로 기록했습니다.

소스·public·기존 문서는 수정하지 않았고, 이 산출물 폴더 안에만 검토 문서·검사 보조 스크립트·JSON·스크린샷을 저장했습니다. 커밋·푸시·배포는 하지 않았습니다. 시작 시점과 비교한 추적 파일 **1,341개 모두 SHA256이 같고**, HEAD도 그대로입니다. [최종 확인](final-checks.json)에 상대 링크 누락 0건, 지역 상세 선택값 100건 일치, 스크린샷 실제 크기와 조건 왕복 대조를 기록했습니다.
