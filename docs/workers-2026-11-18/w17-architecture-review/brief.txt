현재 구조 개요 (반드시 직접 확인할 것)
- 정적 웹이다. React/TS/Vite로 만들고 GitHub Pages(gh-pages)로 배포하며, 서버와 인증키는 없다.
- 화면은 public/data의 JSON과 gz를 직접 읽는다.
- 원본은 data/raw에 있다(gitignore).
- 정제는 scripts/*.py가 하고, 검증은 scripts/validate-*.py와 tests/가 한다.
- 2026-11-17 빌드 기준 JS 546kB, CSS 359kB로, 500kB 경고가 났다.
- 이미 알려진 P2 문제
  - prepare-commerce의 null 부분 합계
  - PopulationPatterns 캐시 키가 file.path만 쓴다
  - prepare-population-patterns에 덮어쓰기 방지가 없다

할 일
1. 현재 구조 실측
   - 계층을 다음과 같이 나눠 지도를 그린다.
     원본 수집 → 정제 스크립트 → 산출 파일·manifest·catalog → 검증 → 배포 → 화면 로딩·캐시 → 컴포넌트
   - 각 계층마다 다음을 적는다.
     - 파일과 스크립트 목록
     - 입력과 출력
     - 데이터 계약을 어디서 정의하는지(스키마, 메타데이터, null 정책, 기간 단위, 공간 단위)
     - 중복되는 로직
   - src에서 다음을 실측한다.
     - 파일별 줄 수와 책임
     - main.tsx 같은 거대 파일
     - 데이터 로딩, 변환, 표시가 섞인 곳
     - 캐시 키 방식
     - 자료별 하드코딩(탭 목록, 제목 매핑 등)
   - public/data에서 자료별 파일 수, 용량, 화면 첫 로딩 크기를 측정한다.
   - npm run build로 번들 구성을 확인한다. 큰 모듈과 코드 분할 여부를 본다.
2. 확장 부담 평가
   - 지하철(역=점, 일·시간대 승하차), 버스(정류장·노선=점·선), 부동산(단지·필지, 거래·시세 월별)을 추가한다고 가정한다.
   - 지금 구조에서 몇 개 파일을 어디까지 고쳐야 하는지 구체적으로 추정한다. 근거로 파일 경로와 줄을 든다.
   - 데이터 양이 커질 때 정적 JSON 방식이 버티는 한계를 수치로 추정한다. 공개 Pages 용량, 첫 로딩 시간, 브라우저 메모리를 본다.
3. 목표 구조 제안
   가. 데이터 관리
   - 주제별 공통 데이터 계약을 정한다. 항목: 스키마, 단위, 기간, 공간 키, null, 출처 메타.
   - manifest와 catalog의 일원화
   - 수집·정제·검증 파이프라인의 공통 틀. 원본 불변, 기존 레코드 불변, 독립 대조 원칙을 유지해야 한다.
   - 버전·캐시 관리
   나. 백엔드
   - 다음 선택지를 비교한다. 비용, 운영 부담, 보안, 서버·인증키 없음이라는 현재 원칙과의 충돌을 표로 정리한다.
     ① 정적 유지 + 사전 집계·분할 파일
     ② 정적 + 브라우저 내 질의(DuckDB-WASM, Parquet 등)
     ③ 서버리스 API
     ④ 별도 API 서버와 DB
   - 어느 시점(데이터 규모, 주제 수)에 다음 단계로 넘어갈지 기준을 정한다.
   다. 프론트엔드
   - 계층 분리를 제안한다: 데이터 접근 계층(로더·캐시), 도메인 변환, 공통 화면 틀(기간·지도·상세·비교·시연·출처), 주제별 모듈(플러그인처럼 등록)
   - 거대 파일 분할과 코드 분할
   - 하드코딩된 자료 목록을 등록부(registry)로 바꾸는 방안
4. 단계별 이전 계획
   - 다음 세 시점으로 나눈다.
     - 지금 바로: 위험이 낮고 효과가 크다. 위 P2 3건을 포함한다.
     - 수평 확장 직전
     - 데이터 규모가 커진 뒤
   - 각 단계에 다음을 적는다.
     - 바뀌는 파일
     - 회귀 방지 방법: 기존 테스트, Playwright PC 16여정, validate-data
     - 되돌리는 방법
   - 화면이 바뀌지 않는 구조 개선을 우선한다.
5. 자기 반박 검토
   - 과잉 설계가 아닌지 확인한다. 현재 규모 대비 비용을 따진다.
   - 데이터 계약 원칙을 깨는 제안이 없는지 확인한다.
   - 근거 없는 수치가 없는지 확인한다.
