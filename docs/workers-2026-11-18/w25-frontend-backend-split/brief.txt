할 일
1. 현재 경계 진단
   - 데이터가 어디서 만들어지고(scripts) 어디에 놓이고(public/data) 어떻게 불려 오는지(src의 fetch, 선로딩, 캐시) 지도로 그린다.
   - 표시 로직과 계산·집계 로직이 섞인 곳을 파일과 줄로 표시한다.
     - 예: 브라우저에서 하는 집계, 비교, 순위
   - 각 곳이 백엔드나 사전 집계로 옮겨야 할 대상인지 판정한다.
2. 분리 선택지 비교. 최소 아래 4안을 다룬다.
   A. 정적 유지 + 데이터만 분리 호스팅
      - 객체 저장소와 CDN에 둔다. 예: Cloudflare R2, S3+CloudFront, GitHub Releases.
      - 프론트는 manifest로 자료 위치와 버전을 찾는다.
   B. 정적 "API" (사전 집계 파일 분할)
      - 질의 단위로 미리 잘라 둔 파일을 요청 시에만 받는다.
      - 대안 기술 예: DuckDB-WASM, Parquet+HTTP range, PMTiles.
   C. 경량 API 서버 + DB
      - 서버 예: FastAPI 또는 Node.
      - DB 예: DuckDB, Postgres/PostGIS.
      - 질의를 서버에서 계산한다.
   D. 서버리스·엣지 함수 + 저장소
      - 예: Cloudflare Workers+R2/D1, Supabase.
   각 안마다 아래를 적는다.
   - 구조도(글 또는 ASCII)
   - 비용: 월 추정. 근거가 있으면 공식 요금 페이지를 인용하고, 아니면 "추정"으로 적는다.
   - 운영 부담
   - 성능: 첫 진입, 상권 첫 진입, 지도 전환
   - 보안
     - 인증키는 서버 쪽에 둔다.
     - 공개 범위
   - 상업 이용(GitHub Pages 제한) 해결 여부
   - 교통·부동산 확장성
   - 데이터 원칙을 지킬 수 있는지
     - 원본 불변
     - null≠0
     - 독립 대조
     - 자료 정의 계약
   - 이전 난이도
3. 데이터 계약 설계(어느 안이든 공통)
   - 자료 manifest 형식. 넣을 항목:
     - id
     - 주제
     - 기간
     - 버전·해시
     - 단위
     - null 의미
     - 출처
     - 갱신일
   - 프론트가 쓰는 데이터 접근 계층(인터페이스)의 초안을 적는다. 화면 코드는 이 계층만 부르게 한다.
   - 정적에서 서버로 바뀌어도 화면 코드가 그대로 남게 하는 방법을 적는다.
4. 저장소 구조안
   - 예: apps/web, pipeline(scripts), api(필요 시), packages/contracts
   - 지금 구조에서 단계적으로 옮기는 순서를 적는다.
   - 레이아웃 이전 단계(1a~5, L)와 어떻게 맞물리는지 적는다. 같은 파일을 동시에 고치지 않게 한다.
5. 권고
   - 지금, 교통 1차 추가 시, 상업 서비스 전환 시의 세 시점별로 권장안을 낸다.
   - 전환 기준: 용량, 동시 사용자, 질의 복잡도, 비용.
   - 사용자가 정할 질문 목록을 붙인다. 예: 상업 서비스 여부, 월 예산, 운영 인력, 로그인 필요 여부.
