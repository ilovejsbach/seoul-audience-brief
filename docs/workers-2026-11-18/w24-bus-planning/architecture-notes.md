# 버스 기획: 정적 배포·공통 구조 독립 검토

2026-11-18 · W24 기획 보조 검토. 브리프 전체, README 데이터 절, DEVELOPMENT_REQUIREMENTS, W17 구조 보고, W18 정적 배포 보고·한도표, W20 확정 목업 보고를 읽었다. 공식 버스 자료의 현재 수·필드·라이선스는 부모/다른 조사자의 확인 대상이며 이 문서에서는 새 웹 요청·다운로드·키 사용·구현을 하지 않았다.

## 핵심 판단

1. 지하철을 교통 1차로 먼저 검증하고, 버스는 정류장·노선·방향·기간을 따로 다루는 계약부터 준비한다. 현 단계에서 교통 메뉴를 활성화하거나 버스 전체 자료를 public에 넣지 않는다.
2. 현재 자료만의 증가도 Pages 여유를 소모한다. 버스 전체 일·시간 자료를 한 JSON에 추가하는 방식은 피하고, 월별 요약 + 선택 지역/노선의 기간 분할 + 요청 시 로딩을 우선 비교한다.
3. 정류장 승하차는 혼잡도·고유 유동인구·OD와 다르다. 작은 파일을 만들기 위해 행정동·상권으로 묶더라도 지표의 뜻과 잃은 정보를 함께 공개해야 한다.

### 한도와 예산

W18이2026-11-18 공식 문서에서 확인한 값은 게시 사이트1GB, 월100GB soft, 현행 Git 경로의 파일50MiB 초과 경고·100MiB 초과 차단이다. **100MiB는 별도의 Pages 파일 한도로 확인된 것이 아니라 현재 Git 배포 경로의 제약**이다. Actions 포장 tar<10GB가 사이트1GB를 해제하지 않으며 LFS를 Pages 우회책으로 삼지 않는다. 이번에는 공식 페이지를 재조회하지 않았다.

- 1GB를10진1,000,000,000B로 보수 계산하면 W18 dist 기준 남은 공간은 **444,652,369B(444.65MB)**다. 공식 GB 환산이 명시되지 않은 점을 고려한1GiB 대조 여유는518,394,193B다. 앞 숫자를 새 버스에 전부 배정하면 기존 자료 성장·지하철·이전 버전 전환 여유가 사라진다.
- W18의 내부 목표800MB를 유지한다면 현재 기준 추가 여유는 **244,652,369B(244.65MB)**다. `버스 허용 예산 = 전체 목표 − 최신 배포 묶음 − 기존 자료 성장분 − 지하철 예산 − 전환 여유`로 정하고, 실제 W23 규모가 나온 뒤 숫자를 채운다. 결과가 음수이면 신규 적재보다 배포 축소·데이터 분리 결정을 앞세운다.
- W18의700MB/90일 내800MB 예측, 단일80MiB는 **전환 준비용 내부 제안**이며 공식 허용 한도가 아니다. 버스 추가 직전에 현재 dist·단일 최대 파일·최근 증가율을 다시 재야 한다.
- 광고주별 비공개 자료·키·로그인이 필요하면 용량과 별개로 권한 경계가 필요하다. 상업 SaaS 운영과 Pages 용도 제한은 W18의 별도 검토 조건이며 데이터 CDN 이전만으로 해결됐다고 보지 않는다. 현재 프로젝트가 금지 용도라는 판정은 하지 않는다.

## 2. 규모 산식: 실제 개수와 예시를 분리

공식 조사에서 다음 변수를 채우기 전에는 정류장·노선 수를 확정하지 않는다.

| 변수 | 뜻 |
|---|---|
| S | 해당 기간에 유효한 고유 정류장 코드 수. 표지·ARS·표준ID·방향의 관계를 먼저 확인 |
| N | 고유 노선 수. 노선번호와 불변ID, 방향·분기 노선의 포함 기준 명시 |
| B | 실제 노선×방향×정류장 순서 조합 수. 정류장과 노선의 전체 곱 S×N으로 대신하지 않음 |
| D / M / H | 일수 / 월수 / 시간 구간 수. 자료가 실제 제공하는 시간 구간을 사용 |
| C | 실제로 제공되는 세분 집단 수. 성별·연령이 별도 주변분포이면 곱하지 않음 |
| E | 제공 OD에서 실제로 관측·공개한 출발→도착 쌍 수. 비공개·미관측을0으로 채우지 않음 |
| b / g | 대표 파일의 평균 행 바이트 / 실제 압축 후 비율. 버스 표본을 안 받은 이번에는 미확인 |

긴 형식의 대략적 행 수는 정류장·일·시간 자료가 `S×D×H`, 노선·정류장·방향·일·시간 자료가 `B×D×H`, 노선·일·시간 합계가 `N×D×H`다. OD는 실제 공개 쌍을 기준으로 `E×D×H`를 상한 검토에 쓰되, 조사표가 이미 기간 집계인지 먼저 확인한다. 밀집 S² 행렬을 실제 제공 행 수로 예측하지 않는다.

**규모 감각용 가정(공식 버스 개수·용량이 아님):** S=10,000, B=40,000, D=365, H=24라면 정류장·시간은8,760만 행, 노선·정류장·시간은3억5,040만 행이다. 길게 편 행당40B라는 추가 가정을 넣으면 평문3.504GB/14.016GB지만, 실제 CSV·JSON 행 크기와 압축률은 아직 모르므로 배포 용량 예측값으로 쓰지 않는다. 원본이24시간 승하차 열을 한 행에 담으면 행 수는 줄어도 한 행의 바이트가 커져 같은40B를 적용할 수 없다.

같은 가정에서 정류장 일합계는365만 행으로 시간별 긴 형식의1/24이다. 월×시간 대표값은288만 행으로 약1/30.4이다. **이는 행 수 비율이며 파일 압축률·수치 손실률이 아니다.** 월평균은 포함 날짜·시간 구간·유효 관측 수를 함께 저장해야 한다.

실제 착수 전 표본 확인 단계에서는 대표 월/노선/지역의 행 수·평문/압축 바이트·해제/파싱 시간·지도 선택 후 요청 파일을 측정한다. W24에서는 표본 다운로드를 하지 않는다. 분할 목표는 단순히100MiB 미만이 아니라 사용자가 한 번에 필요한 작업 세트와 실제 응답 시간이다.

## 4. W20 안에 넣는 구조와 공통 계약

상단은 **교통**, 좌측 자료는 **지하철 / 버스**를 같은 위계로 둔다. 버스 안에서 정류장/노선은 분석 대상 선택이며 지역·상권·지하철과 나란히 상단 탭을 계속 늘리지 않는다. 예정 교통을 활성화하는 구현은 W24 범위가 아니다.

- **중앙 상단 단일 조회 바:** 자료가 지원하는 기간·정류장/노선·방향·승차/하차·시간 기준. 적은 핵심 입력과 추가조건 팝오버를 사용한다. 성별·연령·OD는 확보 판정과 실제 집계 정의가 있는 경우만 노출한다. 좌측에 조회 폼을 중복하지 않는다.
- **중앙 지도·상세:** 정류장은 점, 노선은 순서와 방향을 가진 선이다. 점 선택→관련 노선/시간대 곡선→일·월·계절/두 기간 비교→지도 복귀로 이어진다. OD는 별도 공개 표가 확보됐을 때만 출발/도착 기준 흐름·행렬로 연다. 승하차 주변분포만으로 OD 선을 만들지 않는다.
- **우측 보조:** 선택 정류장/노선의 같은 조건 값·후보 최대3·유효 관측 수·정의/출처를 둔다. ‘혼잡도’ 자료가 없으면 승하차 규모를 혼잡률로 바꾸지 않는다. 동일인의 환승·왕복이 여러 건일 수 있음을 유지한다.
- **배치:** W20의 좌200/우300, 좌접힘64/우접힘0을 출발점으로 한다. 중앙 여백32와 결과 경계2를 뺀 실제 폭은1365에서831px,1920에서1386px이며 양쪽 접으면1267/1822px다. 버스 정류장 중첩·긴 노선명·OD 선이 들어간 실제 읽기 적합성을 증명한 값은 아니다. 점 묶음/확대 시 공개, 방향·후보·범례 가독성을 별도 검사해야 한다.
- **공통으로 재사용:** 기간 선택의 외형, 단일 조회 상태, 지도 viewport·선택/복귀, 상세 틀·같은 조건 후보, 비교 프레임·표시 설정, null/미지원 안내, 출처/버전·요청 취소/캐시 규칙. 지하철과 버스가 같은 시간 단위·집계를 쓴다는 뜻은 아니다.
- **버스 전용:** 표준 정류장ID/ARS/같은 이름의 반대편 정류장, 노선ID·방향·분기·정류장 순서, 정류장 이설/폐지·노선 개편의 유효기간, 버스 운행일/자정 이후 처리, 위치좌표계, 노선 경로와 실제 승객 경로의 차이. 구·동 코드 앞자리나 역 환승 관계를 그대로 적용하지 않는다.

W17의 등록부/공통 로더는 **설계 제안**이다. 버스를 `main.tsx`의 기존 초기 요청 배열에 한 줄 더 넣거나, 현재 구/동 면 채색 계산을 새 점·선 모듈에 강제하는 방식은 피한다. 새 자료 설명서는 최소한 다음을 포함한다.

`datasetId, schemaVersion, sourceId/URL, license, period kind/range/timezone, service-day rule, spatial ID/geometry/version, measure/unit/definition, supported dimensions, null/suppression policy, files(path/hash/bytes/encoding), coverage, provenance`.

버스-지하철 합산은 원본 모집단·기간·승차/하차·환승 포함 여부·결측·지리/시간 코드가 일치할 때에도 대개 **교통 이용 사건 건수의 합**이다. 같은 사람이 지하철→버스를 타면 두 번 셀 수 있어 고유 방문자/통행 수가 아니다. 환승 연결을 포함한 사람·여정 단위 통합은 허용된 매칭자료·분석 권한·중복 제거 정의가 별도로 확인된 경우에만 논의한다. 인구 대비 전환율·광고 노출을 만들어내지 않는다.

### 사용자 결정이 필요한 항목

1. 버스 첫 질문: 정류장 수요 발견, 특정 노선 방향별 수요, 계절 추이, 실제 혼잡도, OD 중 무엇을 먼저 검토할지.
2. 범위: 서울 시내버스만인지, 광역/마을/경기도 유입을 포함할지. 출발지와 도착지가 범위 밖일 때의 포함 정책.
3. 보관 기간·정밀도: 최근 월 시간대 요약을 기본으로 할지, 몇 년의 일별 상세를 유지할지. 계절 비교의 완전한 기간과 동등 비교 기준.
4. 축소 허용: 행정동/상권 묶음의 정보 손실을 허용할지, Top K를 표시만 줄이는 데 쓸지 실제 배포 대상도 제한할지.
5. 운영: 지하철 검증 뒤 버스 표본 조사 시점, 외부 저장/서버 비용 한도, 키·승인자료 관리 담당, 공개/비공개 범위.

## 6. 독립 검토 한계

공식 버스 자료 페이지를 이 하위 검토에서는 열지 않았다. 버스 정류장·노선 수, 원문 행 수/바이트/압축률, 이용권한, 성·연령·OD 제공 여부는 부모와 다른 조사자의 출처 표로 확정해야 한다. 여기의규모는 변수식·명시적 예시이며 실제 확보 예측이 아니다. 플랫폼 한도도 W18의 확인일을 붙인 기존 근거를 재사용했으며 이번에 최신 웹 검증을 하지 않았다.

신규 빌드·성능/메모리·공개 전송·실제 버스 화면 검수는 하지 않았다. W20의 통과는 회색 자리와 대표 입력을 사용한 목업의 통과이지 새 교통 실데이터의 통과가 아니다. 소스·공개자료·기존 문서·기존 원본·Git을 수정하지 않았고 이 문서만 W24 폴더에 작성했다.
